## What the table does

- It starts every eval exactly like live (the first session's choice is the live size).
- Early in the 10 sessions it trades a bit smaller than one-winner size (on average 0.82 x the size, 62% room cap at 10
  sessions left) and, close to the floor, much smaller. With 1-2 sessions left it presses (1.24-1.3 x).
- That is why it fails so rarely: it never lets one loser push the eval under the floor or into the "stuck" zone.

## Why it is not switched on

- **Money:** the whole account slot pays $18 (H1), $34 (H2) and $3 (2021-25) a month less than live. Fewer fails do not pay
  for the slower passes, because a funded 50K is worth about $40 a session and the eval itself costs only $91.80.
- **Speed:** passes slower than 3 weeks rise from 17.3% to 23.3% (H1) and from 13.8% to 21.8% (H2).
- **The owner's choice of 2026-10-25** was room 0.8 for speed and money. This table is the better way to be SAFE, not the
  better way to make money.
- It is a 10 x 201 x 85 table, not a rule a person can read; it would need new code in engine/sizing.

## If the owner ever wants fewer dead evals

Use this table (lam 0.5) instead of going back to room 0.55 + the weekly stop: at the same fail rate it passes 2-4 points
more evals in all three spans and pays the same ($805 / $764 / -$10 vs $804 / $766 / -$14).

## How it was done

`python -X utf8 tools/rd_eval_dp.py` (results `research/lit/rd_eval_dp.json`), `... save` for the runs. Backward induction on a
$25 grid of balance x peak (the peak sets the EOD trailing floor; it locks at +$100), 10 sessions, 28 sizes (k 0.5 / 0.75 / 1
/ 1.25 / 1.5 / 2 / 3 x the one-winner size, room cap 0.4 / 0.6 / 0.8 / 1.0, the $1,000 soft daily loss and 40 micros always on).
Sessions drawn from Jan-Jun 2026 only (80 trades, 48 empty sessions; 1m fills, $1.90 a micro, each trade's own worst open
loss for the intraday floor). The tables were then frozen and replayed through `tools/uprisk.Eval` -> `engine/sizing.lit_qty`
with the state's need_buf / room_f; after session 10 the live safe_eval takes over, exactly as live. The runs `rd_evaldp_*`
store the back-to-back eval path on the real order (one row per traded eval session). Their eval columns use the 50K scorer on
eval-path $, so read the table above, not those columns.
